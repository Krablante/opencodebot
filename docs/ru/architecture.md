# Архитектура

[English](../en/architecture.md) · [Русский](architecture.md) · [Все языки](../README.md)

OpenCodeBot — один процесс Node между Telegram и OpenCodez. OpenCodez владеет выполнением, ID сообщений, историей и веб-пространством. Бот владеет темами Telegram, маршрутизацией ввода, отметками доставки и предпочтениями. Подробности разговора восстанавливаются из OpenCodez, без второй базы истории.

```text
Обновления Telegram → постоянный inbox → обработчики тем → API OpenCodez
                                                         ↓
Сообщения Telegram ← renderer ← события и восстановление ← один SSE на сервер
```

## Границы

[Карта исходников](development.md) показывает владельцев. При изменении нескольких частей важны следующие договорённости:

- Транспорт один раз разворачивает глобальные события `{directory, payload}`. Обработчики получают одну форму для обеих областей зеркалирования.
- Polling сохраняет входящие обновления до подтверждения Telegram. Темы завершают работу независимо; медленный сервер не задерживает следующие пачки.
- Создание темы сначала сохраняет ожидающий запуск. Первый промпт создаёт одну сессию через single-flight темы, привязывает её до изменения модели/System и применяет сохранённый снимок. События настройки не создают вторую тему.
- Живые события и восстановление координируются по сессии. Повторные запросы восстановления объединяются; основные события ждут активную операцию, а не исчезают.
- Renderer получает только опознанные части текста/инструментов основной сессии. Reasoning и неизвестные текстовые delta не проходят в Telegram. Дочерние сессии и точное нормализованное имя `opencode-see delegate` остаются скрытыми.
- После единственного импорта предпочтениями управляет Telegram. Конфигурация установки владеет ключами, адресами, монтированием и пределами провайдеров.

Шлюз артефактов — дополнительный listener в этом процессе. Плагин агента читает файл на своём хосте и передаёт байты с отдельным токеном; JSON шлюза не разрешает чтение файлов. Входящий FILES использует локальные папки или SSH независимо от этого пути. Расшифровка и озвучка обращаются к внешним провайдерам; в образе бота нет моделей для инференса.

## События и выпуск очереди

Текстовый блок становится видимым после завершения его части, а завершение assistant фиксирует доставку. Запрос точного сообщения восстанавливает пропущенные этапы. Каждый здоровый delta не вызывает отдельного HTTP-запроса.

Очередь ждёт и backend idle, и доставленный в Telegram исход предыдущего запуска. Сигналы могут приходить в любом порядке. При необходимости idle-проверка читает текущий логический ход и доставляет потерянный финал до следующего промпта. Ошибка/обрыв получает одно завершающее уведомление; ожидаемые kill/reset/rewind остаются тихими. Вопросы удерживают очередь до ответа. Ручная компакция имеет отдельную блокировку на время своего запроса.

После запроса состояния backend приём в очередь повторно проверяет отмену. Очистка или rewind отменяют прежние поступающие задачи, которые ещё ждут эту проверку. Ответ idle, полученный до начала нового запуска, не может выпустить ожидающие его завершения промпты.

Завершение привязано к каноническим ID сообщений OpenCodez. После отправки промпта очередь ждёт его user-сообщение из SSE или совпадение с отметкой ожидающего Telegram-промпта, прежде чем принимать финал. Восстановление ориентируется на последнее user-сообщение: старые и повторные финалы не завершают новый запуск. Событие idle повторно проверяет состояние backend, если в очереди есть задачи; асинхронные проверки состояния и исхода сохраняют поколение запуска, с которого начались. Пара событий `session.status` idle и `session.idle` может выпустить только одну задачу для одного завершения.

`logical-turn.mjs` следует постоянным связям `turn_id`/`replay_id` компакции и связям напоминаний. Восстановление, экспорт контекста и сессии в Markdown, время/токены и напоминания одинаково определяют исходный запрос человека. Внутренние summaries отмечаются обработанными и не зеркалируются. Автоматическое напоминание посреди запуска восстанавливает содержимое из OpenCodez; уведомление Telegram появляется только после подтверждения приёма. Автоматический повтор, уже сохранённый самим OpenCodez, в том числе перед началом запроса (pre-turn), подтверждается тем же уведомлением без дополнительной отправки промпта.

## Восстановление и ограничения

SSE — основной путь. Обнаружение использует страницы с курсором и пятиминутное перекрытие последней отметки. Восстановление сообщений начинается с пяти записей, затем берёт по двадцать и останавливается на сохранённом курсоре, границе окна или логического хода. После переподключения проверяются только недавние/активные/ожидающие привязки, не более пяти страниц на каждую. Серверы восстанавливаются параллельно, работа внутри сервера упорядочена. Неизменившиеся сессии получают небольшую проверку вместо скачивания всей истории.

Проверка раз в минуту также сверяет исход отслеживаемого незавершённого запуска, даже если отметка обновления сессии не изменилась. Переподключение проверяет незавершённые восстановленные ходы. Когда сервер свободен, свежая история и повторная проверка idle отличают отсутствие финала от продолжающейся работы, вопросов и ожидаемых остановок. Подтверждённый обрыв получает предупреждение в теме и обычное оповещение; постоянная отметка защищает от повторных уведомлений при обычном восстановлении. Условия idle и доставленного исхода для очереди снимаются вместе, чтобы следующий запрос сохранил собственные блокировки.

Обычный HTTP вместе с чтением тела ограничен двумя минутами. `/session` выполняет параллельные запросы по пять секунд. Ручной компакции выделена 21 минута для двадцатиминутного бюджета OpenCodez. Передача файлов ограничена пятнадцатью минутами, SSH-подключение — десятью секундами. Общий backoff хоста применяется к сети/таймаутам, `408`, `429` и `5xx`; подтверждённый `404` сессии удаляет только её состояние.

Inbox хранит до 1 000 обновлений и приостанавливает приём на 16 МиБ; последняя полученная пачка может пересечь предел байтов. На backend работают два обработчика, управление/распознавание/FILES имеют отдельные группы. Остальные пределы памяти и форматы хранения описаны в [состоянии](config-runtime.md#paths-and-state).

Шлюз принимает четыре передачи одновременно; превышение даёт `503` и `Retry-After`. Байты потоково пишутся в собственные временные каталоги, которые удаляются после завершения/ошибки. Ежечасно удаляются опознанные брошенные каталоги старше суток. Облачная multipart-отправка ограничена 32 МиБ памяти; локальный Bot API получает путь общей папки и поддерживает свой предел 2 ГБ без чтения всего файла в RAM бота.

Постоянство распространяется на записанные входящие события и идентификаторы доставки. Авария между внешним действием и его отметкой может повторить действие. Очередь промптов, черновики тем/профилей и незавершённая озвучка исчезают при рестарте. Идентификаторы обычных карточек мастера и сроки удаления сохраняются: при запуске бот удаляет брошенные карточки черновиков и восстанавливает удаление подтверждений. Inbox и маркеры не обещают exactly-once доставку по сети. Сохраняй их вместе и не уничтожай повреждённые данные перед ремонтом.

`health:live` проверяет действующий процесс, прогресс polling/reconcile, Telegram и обязательные API обнаружения. Остановка восстановления инициирует завершение, после чего Compose перезапускает бота. Завершение отменяет обычные запросы, сохраняет отложенное состояние и даёт восемь секунд до выхода. Хранилище описано в [справочнике](config-runtime.md), развёртывание — в [Docker](docker.md).

## Осознанные компромиссы

JSON и append-журналы подходят форумному боту: не требуют базы данных, очереди воркеров или второго способа развёртывания. Индексы доставки занимают память пропорционально сохранённым ID, а проверка остаётся постоянной по стоимости. Отключённая история привязок растёт с историей сессий: она сохраняет смысл остановок тем, названия и ссылки на старые сессии. Перед добавлением базы в большой установке измерь именно эти метаданные и уплотнение журналов.

Упорядоченная обработка событий сервера защищает последовательность доставки, но медленная отправка Telegram задерживает соседнюю сессию этого сервера. Входящие темы и восстановление разных серверов независимы. Разделение живых событий по сессиям потребует правил для событий без сессии и ограниченного приёма; это архитектурный компромисс, а не бесплатная оптимизация.
